# CopyLocker Data Inventory

> ⚠️ **Disclaimer (must appear verbatim at the top of every template)**
>
> All documents in this directory are **technical templates written by the engineering team**
> to reduce the Vendor's cost of drafting compliance documents.
> They are **not legal advice**, do not create a lawyer–client relationship, and do not
> guarantee compliance in any jurisdiction.
> Before use, the Vendor **must** have them reviewed and adapted by qualified legal counsel
> to their own business, data flows, and applicable law.
> The CopyLocker project accepts no liability for legal consequences arising from use of
> these templates.

**Purpose.** This inventory is the factual basis for every other document in the legal pack
(privacy policy section, DPA annex, RoPA entry, DPIA worksheet, DSR runbook). It lists every
data field the CopyLocker SDK collects or the CopyLocker server stores, where it lives, how
long it is kept, and whether it is personal data under GDPR. **We provide facts; the Vendor's
lawyer provides the compliance judgement.**

**Scope.** Data flows into the **Vendor's own Cloudflare account** (Workers / D1 / Durable
Objects / KV / R2 / Queues). The CopyLocker project itself receives, stores, and aggregates
**no** end-user data. The only sub-processor is **Cloudflare, Inc.** Payment providers
(Stripe / Paddle / Lemon Squeezy) are independent controllers for buyer data they collect on
their own checkout pages; CopyLocker only receives their signed webhook events.

**How to read the status column.** `implemented` means the code path exists today (see the
code references in §8). `schema-only` means the table/column exists but the writer is not
wired yet. `in-progress (M5)` / `planned (M6)` mean the behaviour is specified but not yet
shipped — such rows are commitments, not current facts, and are marked **TBD** where a value
(usually a retention period) cannot yet be verified in code.

## 3. Usage & telemetry data

### 3.1 T0 — protocol-derived (on by default, necessary for licensing)

T0 data is a by-product of the licensing protocol itself: activation events, validation
cadence, seat occupancy, version/platform distribution. No separate telemetry payload is
involved. The per-machine source rows are B6/B9/B10 above; the entries below are the
aggregate views.

### 3.2 T1 — aggregate usage telemetry (off by default, consent-gated)

Consent model: the SDK calls the Vendor-supplied `consent()` callback before **every**
upload and skips the upload on falsy; setting `tier: 'T1'` without a `consent` callback is a
deliberate SDK init **error**. `consent_version` is recorded server-side as compliance
evidence.

| C5 | `window_start` | `TelemetryBlock` | Same as C4 | Raw: 30 days | No (coarse window anchor, not an event timestamp) | TLS; platform at rest | None | **in progress (M5)** |
| C6 | `session_count` | `TelemetryBlock` | Raw 30 days → D1 `telemetry_rollup` | Raw 30 days; rollup 3 years | No (counter) | TLS; platform at rest | None | **in progress (M5)** |

**Deletion boundary (must be restated in the privacy policy).** On a machine-level deletion:
DO activation rows, D1 `machines` rows, and R2 raw records are deleted; PII fields in audit
logs are replaced with a tombstone while the hash chain is preserved; **HLL sketches and
rollup counters are not retroactively modified** — they contain no personal data, and
retroactive edits would destroy historical comparability and audit integrity. The deleted
device stops contributing to **future** aggregates.

## 5. Payment data

Card data never touches CopyLocker infrastructure. Checkout happens on the payment
provider's page; the provider is an independent controller for the buyer relationship.
CopyLocker receives only the provider's **signed webhook**, normalized to the fields below
(`crates/copylocker-worker/src/webhook.rs`).

| # | Field | Source | Storage | Retention | Personal data? | Encryption | Shared with | Status |
|---|---|---|---|---|---|---|---|---|
| E1 | `provider` (`stripe`/`paddle`/`lemonsqueezy`) | Webhook endpoint path | D1 `subscriptions`, `billing_events` | Subscription lifetime | No | Webhook signature verification at ingress; TLS | Payment provider (as source controller) | implemented |
| E2 | `event_id`, `event_ts` | Webhook payload | D1 `billing_events` (idempotency) | Subscription lifetime | No | TLS; platform at rest | None | implemented |
| E3 | `external_id` (provider's subscription id) | Webhook payload | D1 `subscriptions.external_id` | Subscription lifetime | Pseudonymized — resolvable to a buyer only inside the provider's own system | TLS; platform at rest | Payment provider | implemented |
| E4 | `license_id` (from `copylocker_license_id` metadata/custom_data) | Webhook payload metadata | D1 `subscriptions.license_id` | Subscription lifetime | Pseudonymous (see A1) | TLS; platform at rest | None | implemented |
| E5 | `event_kind` (started/renewed/payment failed/recovered/cancel/period ended/refund) + `period_start`, `period_end`, `billing_period` | Webhook payload | D1 `subscriptions` | Subscription lifetime | No | TLS; platform at rest | None | implemented |

**Explicitly not received or extracted:** card number, CVC, cardholder name, billing
address, buyer email/name from the webhook payload (the normalizers read only the fields
listed above), or any payment-instrument data. Vendors must not place buyer PII in the
`copylocker_license_id` metadata field (hex 16-byte id, enforced by validation).
